## Critical Findings

### CR-01 — Swallowing non-404 commercetools errors during DMN payment resolution can misresolve payments

- Severity: Critical
- Category: Bug / reconciliation safety
- Location: `processor/src/services/nuvei-payment.service.ts:1266-1279`

Problem: `resolveDmnPayment()` catches every error from `ctPaymentService.getPayment({ id: merchantUniqueId })` whenever a DMN also has a session token. It logs a warning and falls through to session-token lookup without checking whether the original error was actually `ResourceNotFound`.

Impact: commercetools 5xx/auth/network failures are hidden as a normal fallback path. Under degraded CT conditions the processor can reconcile a DMN by session token even though direct `merchant_unique_id` lookup failed for an infrastructure reason, weakening the wrong-payment protection around financial events.

Recommended fix: only fall back when `isResourceNotFoundError(error)` is true. Rethrow all non-404 errors even if a session token is present.

## Warning Findings

### WR-01 — Web SDK ignores `storePaymentDetails`

- Severity: Warning
- Category: Bug
- Location: `enabler/src/components/web-sdk-card.ts:67-82`

Problem: `submit()` computes `clickOptions?.storePaymentDetails ?? options.storePaymentDetails` and immediately discards it with `void`.

Impact: callers cannot request stored-payment/tokenization behavior through the public `SubmitOptions` contract.

Recommended fix: capture the computed flag and pass it to Nuvei Web SDK in the supported field for stored payment details, or remove the public option until implementation is supported.

### WR-02 — Simply Connect cancellation still enters backend confirmation polling

- Severity: Warning
- Category: Bug / UX correctness
- Location: `enabler/src/components/simply-connect-card.ts:119-137`

Problem: `handleCheckoutResult()` strips `cancelled` from the Nuvei result and always calls `confirmPaymentResult()`.

Impact: shopper cancellation is treated like a payment result requiring backend confirmation, causing unnecessary processor calls and confusing delayed failure behavior.

Recommended fix: branch on `result.cancelled` before polling. Return a safe failure result or call the configured error/completion callback directly.

### WR-03 — Web SDK terminal `ERROR` and cancellation still enter backend confirmation polling

- Severity: Warning
- Category: Bug / UX correctness
- Location: `enabler/src/components/web-sdk-card.ts:130-144`

Problem: `handleWebSdkResult()` forwards only `transactionStatus` and `errCode`, ignoring `cancelled` and `errorDescription`, then always calls `confirmPaymentResult()`.

Impact: terminal frontend errors and cancellations are not surfaced immediately and may become misleading pending/technical confirmation errors.

Recommended fix: handle `res.result === "ERROR"` and `res.cancelled === true` locally before confirmation polling, using `onError`, `onComplete({ isSuccess: false })`, or a documented cancellation callback path.

### WR-04 — Shared confirmation helper discards Nuvei terminal result details

- Severity: Warning
- Category: Code quality / behavior clarity
- Location: `enabler/src/services/api-service.ts:82-128`

Problem: `confirmPaymentResult()` receives a Nuvei result but discards it with `void result`.

Impact: frontend terminal signals such as cancellation, SDK validation errors, or SDK-level error codes cannot influence confirmation behavior. All outcomes poll the processor, increasing latency and hiding actionable SDK errors.

Recommended fix: either inspect terminal frontend states before polling or change the helper signature so it only receives values it actually uses.

### WR-05 — Simply Connect sends hardcoded sandbox email to Nuvei

- Severity: Warning
- Category: Data quality / production safety
- Location: `enabler/src/components/simply-connect-card.ts:102-109`

Problem: `billingAddress.email` is always `"sandbox@example.com"`.

Impact: real transactions can send a placeholder shopper email to Nuvei, degrading authorization evidence and merchant support data.

Recommended fix: accept shopper email through the enabler options when available and omit the email field when it is unavailable.

### WR-06 — Web SDK sends hardcoded sandbox email to Nuvei

### WR-09 — Synthetic DMN checksum is written to the wrong form field

- Severity: Warning
- Category: Bug / test harness correctness
- Location: `examples/nuvei-web-ui/api-e2e-test.mjs:181-201`

Problem: when `NUVEI_SECRET_KEY` is set, the script computes a checksum into `dmnBody.checksum` while the payload already contains `advanceResponseChecksum: "mock-checksum"`.

Impact: the processor receives both fields and may validate the stale mock checksum field, so the E2E scenario can reject a DMN even though the script computed a real checksum.

Recommended fix: write the computed digest to `dmnBody.advanceResponseChecksum`, or remove the mock field before serialization if the processor intentionally accepts `checksum`.

### WR-10 — Mock server configures invalid credentialed CORS

- Severity: Warning
- Category: Security / browser integration
- Location: `examples/nuvei-web-ui/mock-commercetools-server.mjs:5-12`

Problem: the mock server sets `Access-Control-Allow-Origin: *` together with `Access-Control-Allow-Credentials: true`.

Impact: browsers reject credentialed requests with wildcard origin, and the configuration normalizes an unsafe pattern for payment tooling.

Recommended fix: echo a validated local origin in development, or omit `Access-Control-Allow-Credentials` when wildcard origin is used.

### INFO-03 — Simply Connect loader cache policy differs from Web SDK loader

- Severity: Info
- Category: Maintainability
- Location: `enabler/src/services/simply-connect-sdk.ts:51-93`
