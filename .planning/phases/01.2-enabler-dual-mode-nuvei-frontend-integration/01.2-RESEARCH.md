## Summary

Phase 1.2 has three independent work tracks that can run largely in parallel: processor contract cleanup (remove `embedded`), enabler class split (add `NuveiWebSdkEnabler`, rename SC artifacts, delete dropin), and harness migration (move useful pieces from `testing/` to `examples/nuvei-web-ui`). The cross-package parity test update and example UI that exercises both modes are gating artifacts that land in Wave 2 after the other tracks.

The most important architectural fact is the **submission-ownership difference**: Simply Connect's widget owns its pay button and submission (`componentHasSubmit=false`, `submit()` throws), while Web SDK requires the merchant to own the pay button and call `sfc.createPayment()` (`componentHasSubmit=true`). Getting this wrong in the Web SDK component is the most user-visible correctness issue.

The second critical fact is **callback result shape**: Simply Connect `onResult` returns `transactionStatus` (string); Web SDK `createPayment()` callback returns `result` (string). These are different field names on the raw SDK result objects. Each mode adapter normalizes its own raw result before passing to the shared `confirmPaymentResult`. Do not reuse the same raw-result type across modes.

**Primary recommendation:** Wave 0 can start immediately with three independent tracks (A: processor embedded removal, B: enabler loader/file split, C: examples scaffolding). Wave 1 adds Web SDK card implementation and mode-class creation. Wave 2 closes with parity test update and example UI wiring.

### Pattern 1: Web SDK Initialization (3-phase)

```typescript
// Source: https://docs.nuvei.com/documentation/accept-payment/web-sdk/quick-start-for-web-sdk/

// Phase A: load safecharge.js → SafeCharge global
declare global { interface Window { SafeCharge?: (opts: SafeChargeOptions) => SafeChargeInstance } }

// Phase B: instantiate SDK and Nuvei Fields, attach to placeholder
const sfc = SafeCharge({ env: 'int' | 'prod', merchantId, merchantSiteId });
const scFields = sfc.fields({ fonts: [] });
const scard = scFields.create('card', { style: {} });
scard.attach(document.getElementById('card-field-placeholder'));
// card fields are now rendered; merchant provides their own pay button

// Phase C: on merchant button click, call createPayment
sfc.createPayment({
  sessionToken: '<from openOrder via processor POST /payments/session>',
  clientUniqueId: '<cartId>',
  cardHolderName: '<name>',
  paymentOption: scard,        // the Nuvei Fields instance, not a string
  billingAddress: { email, country },
}, (res: SafeChargeResult) => {
  // res.result === 'APPROVED' | 'DECLINED' | 'PENDING' | 'ERROR'
  // res.transactionId — optional fiscal transaction ID
  // res.errCode, res.errorDescription
  // 3DS is handled internally; challenge UI appears if needed
  normalizeWebSdkResult(res);
  confirmPaymentResult(...);
});
```

### Pattern 3: Mode Facade

```typescript
// Claude's discretion for exact shape; constraint: mode required, fails before external effects

export class NuveiEnabler implements PaymentEnabler {
  constructor(
    private readonly opts: EnablerOptions,
    private readonly mode: 'simply-connect' | 'web-sdk',
  ) {
    validateEnablerOptions(opts);
    if (mode !== 'simply-connect' && mode !== 'web-sdk') {
      throw modeUnsupported(mode);
    }
  }

  async createComponentBuilder(type: string): Promise<PaymentComponentBuilder> {
    if (type !== PaymentMethod.card) throw methodUnsupported(type, 'component');
    return this.mode === 'simply-connect'
      ? new SimplyConnectCardBuilder(this.opts)
      : new WebSdkCardBuilder(this.opts);
  }
  // No createDropinBuilder (embedded removed)
}
```

### Anti-Patterns to Avoid

- **Sharing `loadNuveiSdk` across modes**: The Simply Connect loader sets `window.checkout`; the Web SDK loader sets `window.SafeCharge`. These are different globals from different script URLs. A single loader that "tries both" is wrong and will cause subtle failures.
- **Passing raw SDK result to `confirmPaymentResult`**: `CheckoutResult.transactionStatus` ≠ `SafeChargeResult.result`. Normalizing inside each mode adapter prevents future confusion when field names diverge.
- **`componentHasSubmit=true` on Simply Connect card**: The widget owns its own pay button. Setting `componentHasSubmit=true` on the SC component would cause Checkout to call `submit()` externally, which currently throws and is documented as intentional.
- **Mode as a payment method key**: `web-sdk-card` must never appear in `paymentMethodOptions`. The processor key is always `card`; mode is an enabler-side concern.
- **Leaving `embedded` in `SupportedPaymentDropinsData` enum**: TypeBox schema has `DropinType.EMBEDDED` and `DropinType.HPP`. If not removed from the schema, the TypeBox type still accepts `embedded` in dropin requests.

## Specific Question Answers

### Q1: Web SDK globals and functions used for card mode

[CITED: https://docs.nuvei.com/documentation/accept-payment/web-sdk/quick-start-for-web-sdk/]

**Script URL**: `https://cdn.safecharge.com/safecharge_resources/v1/websdk/safecharge.js`
**Global**: `window.SafeCharge` (capital S, capital C) — a factory function.

**Initialization chain** (all 3 must complete before payment submission):
1. `SafeCharge({ env, merchantId, merchantSiteId })` → returns `sfc` instance
2. `sfc.fields({ fonts: [...] })` → returns `ScFields` (Fields factory)
3. `ScFields.create('card', { style: {} })` → returns `scard` (the card field widget)
4. `scard.attach(domElement)` → renders card number/expiry/CVV fields into the DOM element

**Payment submission**:
- `sfc.createPayment({ sessionToken, clientUniqueId, cardHolderName, paymentOption: scard, billingAddress }, callback)`
- Note: `paymentOption` receives the `scard` instance object, NOT a string like `"card"`.
- Callback receives `{ result, transactionId, errCode, errorDescription, ... }` — `result` is the status field.

**3DS**: handled internally by `createPayment()`. No explicit `authenticate3d()` call needed for standard managed flow. If 3DS challenge is required, the SDK renders it within the same `createPayment()` call.

**Type declaration needed** (new in Phase 1.2):
```typescript
interface SafeChargeOptions { env: 'int' | 'prod'; merchantId: string; merchantSiteId: string; }
interface SafeChargeFieldsOptions { fonts?: Array<{ cssUrl: string }>; }
interface SafeChargeCardField {
  attach(el: Element): void;
  // scard instance is passed as paymentOption, not called directly
}
interface SafeChargeResult {
  result: 'APPROVED' | 'DECLINED' | 'PENDING' | 'ERROR';
  transactionId?: string;
  errCode?: string | number;
  errorDescription?: string;
  cancelled?: boolean;
}
interface SafeChargeInstance {
  fields(opts: SafeChargeFieldsOptions): { create(type: 'card', opts: object): SafeChargeCardField };
  createPayment(params: object, callback: (res: SafeChargeResult) => void): void;
}
declare global { interface Window { SafeCharge?: (opts: SafeChargeOptions) => SafeChargeInstance; } }
```

### Q2: Web SDK card submit flow vs. Simply Connect checkout()

**Simply Connect** (`checkout.js` / `window.checkout`):
1. Load `checkout.js` → `window.checkout` function
2. Call `checkout({ sessionToken, merchantId, merchantSiteId, env, amount, currency, renderTo, onResult })`
3. Widget renders full payment UI including card form AND built-in pay button inside `renderTo`
4. User fills card details, clicks widget's pay button
5. Widget internally runs 3DS if needed
6. `onResult(result)` fires: `result.transactionStatus` is `'APPROVED'`/`'DECLINED'`/`'ERROR'`
7. **Submit trigger**: widget-owned pay button — `component.submit()` is invalid (throws)
8. `componentHasSubmit = false`

**Web SDK** (`safecharge.js` / `window.SafeCharge`):
1. Load `safecharge.js` → `window.SafeCharge` factory
2. `const sfc = SafeCharge({ env, merchantId, merchantSiteId })`
3. `const scard = sfc.fields({}).create('card', { style })`
4. `scard.attach(domEl)` — renders ONLY the card fields (number/expiry/CVV) in the merchant's element
5. Merchant renders their own pay button elsewhere on the page
6. On button click: `sfc.createPayment({ sessionToken, paymentOption: scard, billingAddress, cardHolderName }, callback)`
7. SDK internally runs 3DS if needed, shows challenge UI if required
8. `callback(res)` fires: `res.result` is `'APPROVED'`/`'DECLINED'`/`'PENDING'`/`'ERROR'`
9. **Submit trigger**: merchant-controlled button, merchant calls `createPayment()` — `component.submit()` IS valid
10. `componentHasSubmit = true`

**Key protocol difference for `confirmPaymentResult`**:
- SC normalizer maps: `{ transactionStatus: result.transactionStatus, sessionToken: result.sessionToken, errCode: result.errCode }`
- Web SDK normalizer maps: `{ transactionStatus: res.result, sessionToken: undefined /* not in callback */, errCode: res.errCode }`

The Web SDK `createPayment()` callback does NOT return the session token. The normalizer should use `knownSessionToken` from `createPayment()` processor response, as already done by `confirmPaymentResult` (which ignores `result.sessionToken` and uses the `knownSessionToken` parameter — D-11 already handles this correctly).

### Q3: 3DS behavior differences between the two modes

| Aspect | Simply Connect | Web SDK |
|--------|---------------|---------|
| 3DS trigger | Automatic inside `checkout()` | Automatic inside `createPayment()` |
| Frictionless flow | Widget handles silently | SDK handles silently |
| Challenge flow | Widget renders challenge UI inside widget area | SDK renders challenge UI (overlaid) |
| Merchant visibility | None — widget reports final outcome via `onResult` | None — SDK reports final outcome via `createPayment` callback |
| Explicit `authenticate3d()` | Not used | Available but not needed for standard Phase 1.2 flow |
| Result field after 3DS | `result.transactionStatus` | `res.result` |
| 3DS abandonment | `result.transactionStatus = 'DECLINED'` or `result.cancelled = true` | `res.result = 'DECLINED'` or `res.cancelled = true` |
| Impact on processor confirm | Same — simply calls `POST /payments/confirm/:id` | Same — calls `POST /payments/confirm/:id` |

**Bottom line**: From Phase 1.2's perspective, 3DS is fully transparent for both modes. Neither mode requires the enabler to implement a separate `authenticate3d()` call. The difference only matters for Phase 2 evidence capture: evidence must label which mode was used per scenario.

### Q9: Most dangerous thing to get wrong on processor side

**Highest risk: `embedded` still accepted by `isSupportedPaymentMethod` after registry update, creating orphaned Nuvei orders.**

The current flow in `NuveiPaymentService.createPaymentSession()` calls `isSupportedPaymentMethod(method)` using the `PAYMENT_METHOD_REGISTRY` from `payment-components.dto.ts`. When `embedded` is removed from the registry, `isSupportedPaymentMethod('embedded')` returns `false` and the endpoint returns a safe error — correct.

**However**, the `PaymentMethodOptionsSchema` in `nuvei-payment.dto.ts` uses `Type.Optional(Type.Unknown())` for `paymentMethodOptions`. TypeBox accepts any object. So the method key check must stay in the service layer (where it already is), not rely on schema validation alone. This is currently correct — the schema intentionally allows unknown keys. The real guard is in the service. **No change needed to the schema** — the registry-based service check is the guard.

**Second risk: `SupportedPaymentDropinsData` TypeBox schema still contains `DropinType.EMBEDDED`.**

`payment-components.dto.ts` defines:
```typescript
const DropinType = Type.Enum({ EMBEDDED: "embedded", HPP: "hpp" });
export const SupportedPaymentDropinsData = Type.Object({ type: DropinType });
```

The `SupportedPaymentComponentsSchema` is the **response** schema for `GET /payment-components`. It doesn't gate incoming requests. However, it's also used as a TypeScript type. If left unchanged, `getSupportedPaymentComponents()` returns `{ dropins: [] }` but the TypeBox type still permits `embedded` in the `dropins` array. This is a latent inconsistency but not a runtime failure. **Clean up the enum** to remove `EMBEDDED` and avoid drift.

**Third risk: parity test passes after processor change but before enabler change, creating a window where tests give false confidence.** The fix: update both registries in the same plan/wave, then update the parity test as a separate atomic step that only runs when both sides are complete.

## Common Pitfalls

### Pitfall 1: Web SDK `paymentOption` is the `scard` instance, not the string `"card"`

**What goes wrong:** Passing `paymentOption: "card"` (a string) to `sfc.createPayment()` instead of the Nuvei Fields instance `scard`. The SDK silently fails or returns an error.
**Why it happens:** The documentation sometimes refers to "card payment" and developers infer the string "card" is the value.
**How to avoid:** Always pass `paymentOption: scard` where `scard = ScFields.create('card', {})`.
**Warning signs:** `createPayment()` callback returns `result: 'ERROR'` with `errCode` immediately; no 3DS challenge.

### Pitfall 2: Web SDK `createPayment()` callback uses `result` not `transactionStatus`

**What goes wrong:** Normalizer reads `res.transactionStatus` (Simply Connect convention) on a Web SDK callback result. Gets `undefined` → mapped as unknown → returns `pending` for every payment.
**Why it happens:** The existing `CheckoutResult` type has `transactionStatus`; developers copy-paste it to Web SDK.
**How to avoid:** Separate `SafeChargeResult` interface with `result: string`. `normalizeWebSdkResult` maps `res.result` to the shared normalized shape.
**Warning signs:** All Web SDK payments report `pending` regardless of actual Nuvei status.

### Pitfall 3: Accessing `result.sessionToken` from Web SDK callback

**What goes wrong:** Web SDK `createPayment()` callback does NOT return `sessionToken`. Attempting to use `res.sessionToken` as `knownSessionToken` gives `undefined`.
**Why it happens:** Simply Connect `onResult` does return `sessionToken` in some configurations.
**How to avoid:** Always use the `sessionToken` received from `POST /payments/session` processor response (`paymentRes.sessionToken`), never from the browser SDK callback. This is already the correct pattern from D-11 / Phase 1.1.1.
**Warning signs:** `confirmPaymentResult` called with `knownSessionToken = undefined` → processor returns 400/401.

### Pitfall 4: Module-scope `sdkLoadPromise` shared across Simply Connect and Web SDK loaders

**What goes wrong:** If both loaders reference the same `sdkLoadPromise` variable, the second loader resolves with the first SDK's value.
**Why it happens:** Copy-paste from `nuvei-sdk.ts` without checking module isolation.
**How to avoid:** Each loader module (`simply-connect-sdk.ts`, `web-sdk.ts`) has its own module-scope `let loadPromise: Promise<...> | undefined`. Never shared.
**Warning signs:** Web SDK enabler receives `window.checkout` function instead of `window.SafeCharge` instance.

### Pitfall 5: `embedded` removed from enabler registry but `DropinType.EMBEDDED` left in TypeBox schema

**What goes wrong:** `GET /payment-components` advertises `{ dropins: [] }` (correct) but the TypeBox schema still has `EMBEDDED` in the `DropinType` enum. Old clients can still technically parse `embedded` in the response schema type. More critically, TypeScript code that constructs a `SupportedPaymentComponentsSchemaDTO` still sees `EMBEDDED` as a valid type, creating false confidence.
**How to avoid:** Remove `EMBEDDED` from the `DropinType` const in `payment-components.dto.ts` as part of the same commit that removes it from `PAYMENT_METHOD_REGISTRY`.

### Pitfall 6: Enabling Simply Connect card component `submit()` to delegate to Web SDK

**What goes wrong:** Phase 1.2 has two card implementations. Someone wires the SC card's `submit()` to call into Web SDK's `sfc.createPayment()`.
**Why it happens:** Premature abstraction or confusion between mode lifecycle responsibilities.
**How to avoid:** The SC card `submit()` must still throw with "Simply Connect handles submission internally via the widget pay button." Only the Web SDK card component exposes a meaningful `submit()`.

### Web SDK card component submit lifecycle

```typescript
// enabler/src/components/web-sdk-card.ts
export class WebSdkCardBuilder implements PaymentComponentBuilder {
  public componentHasSubmit = true;  // merchant calls component.submit()
  constructor(private readonly opts: EnablerOptions) {}
  build(config: ComponentOptions): PaymentComponent {
    return new WebSdkCardComponent(this.opts, config);
  }
}

class WebSdkCardComponent implements PaymentComponent {
  private sfc: SafeChargeInstance | undefined;
  private scard: SafeChargeCardField | undefined;
  private sessionToken = '';
  private paymentReference = '';
  private readonly api = apiService({ ... });

  mount(selector: string): void {
    this.init(selector).catch((err) => this.baseOptions.onError?.(err));
  }

  submit(): void {
    if (!this.sfc || !this.scard) throw new Error('WebSdkCardComponent: not yet mounted');
    this.sfc.createPayment(
      {
        sessionToken: this.sessionToken,
        clientUniqueId: '<cartId from paymentRes>',
        cardHolderName: '<placeholder or from options>',  // Phase 4 sources real data
        paymentOption: this.scard,
        billingAddress: { email: 'sandbox@example.com', country: 'US' },  // Phase 4 fences
      },
      (res) => { this.handleWebSdkResult(res); },
    );
  }

  private async init(selector: string): Promise<void> {
    const [paymentRes, sfc] = await Promise.all([
      this.api.createPayment({ paymentMethodOptions: { card: {} } }),
      loadWebSdk({ env: ..., merchantId: ..., merchantSiteId: ... }),
    ]);
    this.sessionToken = paymentRes.sessionToken;
    this.paymentReference = paymentRes.paymentReference;
    this.sfc = sfc;
    const scFields = sfc.fields({});
    this.scard = scFields.create('card', {});
    this.scard.attach(document.querySelector(selector)!);
  }

  private handleWebSdkResult(res: SafeChargeResult): void {
    const normalized = { transactionStatus: res.result, errCode: res.errCode };
    void confirmPaymentResult(
      normalized, this.paymentReference, this.sessionToken, this.api,
      this.baseOptions.onComplete, this.baseOptions.onError, this.baseOptions.onPending,
    );
  }
}
```
