# Phase 1.2: Enabler dual-mode Nuvei frontend integration - Context

**Gathered:** 2026-06-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Restructure the browser enabler so Nuvei Simply Connect and Nuvei Web SDK can both be represented as explicit, separately-tested frontend integration modes. The current enabler has one live Simply Connect path; Phase 1.2 adds an evidence-ready Web SDK card path, removes unproven embedded/drop-in support for now, and cleans up the temporary local testing harness so Phase 2 can capture sandbox evidence for both frontend modes.

This phase does not add wallets, APMs, stored payment methods, production readiness claims, full Checkout data correctness, or reconciliation hardening. Processor payment routes stay unchanged except for supported-method contract cleanup from removing embedded.

</domain>

<decisions>
## Implementation Decisions

### Public API and mode selection
- **D-01:** Expose separate explicit classes for Nuvei frontend modes: `NuveiSimplyConnectEnabler` and `NuveiWebSdkEnabler`.
- **D-02:** Keep `NuveiEnabler` exported as a facade/factory, not the only concrete implementation.
- **D-03:** `NuveiEnabler` facade must require an explicit mode; no silent default to Simply Connect. This is an intentional breaking cleanup before sandbox evidence.
- **D-04:** Mode-specific enablers use the same payment method key, `card`. Integration mode must not become a processor payment method key such as `web-sdk-card`.
- **D-05:** `NuveiSimplyConnectEnabler.createComponentBuilder("card")` and `NuveiWebSdkEnabler.createComponentBuilder("card")` are both valid. Which lifecycle is used is determined by the class/facade mode, not the payment method key.

### Component and source architecture
- **D-06:** Keep the project broadly type-first (`components/`, `services/`, public `payment-enabler/` contracts) rather than moving everything to mode-first top-level folders, but clean up the current ambiguity and coupling.
- **D-07:** Rename/split current generic names that are actually Simply Connect-specific. `nuvei-sdk.ts` must stop being the ambiguous home for all browser Nuvei SDK behavior.
- **D-08:** Share infrastructure only between modes: processor `apiService`, payment-session creation, confirmation helper, and small DOM/mount helpers if useful.
- **D-09:** Do not share SDK loading, rendering lifecycle, submit ownership, 3DS handling, or raw result interpretation between modes until Phase 2 evidence proves a safe common abstraction.
- **D-10:** Use separate loader modules: one for Simply Connect `checkout.js` and one for Web SDK `safecharge.js`. Each loader owns its own global type, script URL, cache, failure behavior, and tests.
- **D-11:** Normalize raw SDK result shapes inside each mode adapter. Shared confirmation code should receive only the minimal normalized fields it actually needs, not raw Simply Connect/Web SDK payloads.

### Scope of supported methods
- **D-12:** Remove embedded/drop-in support everywhere at this stage. The connector becomes card-only for browser methods until sandbox evidence justifies more.
- **D-13:** Processor `/payment-components` and accepted `paymentMethodOptions` must advertise/accept only `card`; `embedded` is removed from processor and enabler parity expectations.
- **D-14:** Remove enabler drop-in builder support and public embedded/drop-in examples/docs for now. Do not keep compatibility aliases for embedded.
- **D-15:** No wallets, APMs, express payments, stored payment methods, or Web SDK non-card flows are added in Phase 1.2.

### Web SDK evidence-ready path
- **D-16:** Add a Web SDK **card-only** path that is evidence-ready for Phase 2: it can create a processor payment session, render Web SDK card fields, submit through Web SDK, and feed tri-state confirmation.
- **D-17:** The Web SDK path does not need full production polish in this phase, but it must be real enough for Nuvei sandbox evidence capture. Stubs/scaffolds that cannot perform a payment are not acceptable.
- **D-18:** Web SDK component submit ownership differs from Simply Connect: Web SDK card component exposes `submit()` and sets `componentHasSubmit=true`; the caller/Checkout/example UI triggers submission.
- **D-19:** Simply Connect remains internally managed: its widget owns its pay button/submission lifecycle unless implementation evidence proves otherwise.
- **D-20:** Phase 1.2 may keep temporary sandbox/evidence placeholder shopper/billing data for Web SDK if needed, but it must be clearly marked non-production and must not erase Phase 4 data-correctness work. Do not claim production readiness for hardcoded evidence data.

### Compatibility and migration stance
- **D-21:** Breaking cleanup is acceptable in Phase 1.2 because this is still pre-sandbox/pre-production and the goal is to avoid carrying unproven abstractions forward.
- **D-22:** Do not preserve deprecated embedded/drop-in exports or default `NuveiEnabler` behavior solely for compatibility.
- **D-23:** Update docs and examples to make the break explicit: card-only, explicit mode selection, Simply Connect and Web SDK as separate modes.

### Testing expectations
- **D-24:** Add/adjust adapter tests for both mode-specific enablers: Simply Connect must keep existing behavior; Web SDK must prove loader/render/submit/result-confirm flow at the unit boundary.
- **D-25:** Update cross-package card-only parity tests so processor advertised methods, processor accepted methods, and enabler buildable methods all align on `card` only.
- **D-26:** Test that the facade requires explicit mode and rejects missing/unsupported mode before any processor call or SDK load.
- **D-27:** Test that mode-specific loaders and result handlers do not call each other or depend on each other's globals.

### Example web UI and harness cleanup
- **D-28:** Clean up the temporary `testing/` harness as part of this stage. It is currently a messy temporary directory and should not remain the Phase 2 evidence entry point.
- **D-29:** Create/move the maintained Nuvei integration example to `examples/nuvei-web-ui`.
- **D-30:** `examples/nuvei-web-ui` should be a self-contained npm package with its own `package.json`, scripts, and README/instructions.
- **D-31:** Remove Postman collection/environment assets entirely. Do not archive them as legacy docs. Any useful manual flows must move into the example web UI, scripts, or docs.
- **D-32:** Move useful local mock commercetools server, DMN/tunnel helpers, and ledger inspection support into the example app with cleaner naming/scripts.
- **D-33:** The example web UI must support choosing between Simply Connect card mode and Web SDK card mode so Phase 2 can capture evidence for both.
- **D-34:** The example app should exercise the real enabler bundle/source and processor API contracts; it must not become a fake payment demo divorced from the connector behavior.

### Claude's Discretion
- Exact facade API shape for mode selection, as long as mode is explicit and unsupported/missing mode fails before external effects.
- Exact file names and helper boundaries inside the type-first folder structure.
- Exact example app framework/build tooling, as long as it is self-contained, npm-based, and lightweight.
- Exact safe placeholder data shape for Web SDK evidence, as long as it is clearly sandbox-only and Phase 4 remains responsible for real data sourcing.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `apiService` already owns `POST /payments/session` and `POST /payments/confirm/:id`; it is the correct shared infrastructure for both frontend modes.
- `confirmPaymentResult()` already maps tri-state processor outcomes to `onComplete`, `onError`, and `onPending`; reuse it from both mode adapters after each adapter normalizes its raw SDK result.
- Current card/drop-in components already know how to call processor session creation, store `sessionToken`/`paymentReference`, and invoke confirmation.
- Existing enabler tests cover API service, card, drop-in, SDK loading, and public enabler behavior; they provide the test style for new mode adapter coverage.
- Existing local mock server/browser harness under `testing/` contains useful ledger and flow visibility, but needs relocation and cleanup.

### Established Patterns
- Enabler public APIs are TypeScript interfaces exported from `payment-enabler.ts` and concrete classes from `index.ts`.
- Method registries are mirrored between enabler and processor and protected by parity tests; removing `embedded` must update both sides.
- Processor payment method keys are business payment methods, not frontend integration modes. Keep `card` as the method key for both Simply Connect and Web SDK.
- SDK script loading is currently cached at module scope. Separate loaders should each own their cache and global lookup.
- Existing code currently conflates Simply Connect with generic Nuvei SDK naming; Phase 1.2 should make that explicit.

### Integration Points
- `NuveiSimplyConnectEnabler` connects to current `checkout.js` / `window.checkout` flow.
- `NuveiWebSdkEnabler` connects to a new Web SDK `safecharge.js` loader and card component submit lifecycle.
- Both modes connect to the same processor APIs and tri-state confirmation helper.
- The example web UI connects browser enabler mode selection, local/real processor URL, mock CT/DMN helper scripts, and Phase 2 evidence capture.

</code_context>

<specifics>
## Specific Ideas

- User explicitly wants both Simply Connect and Web SDK supported eventually; Phase 1.2 must create the missing Web SDK path instead of pretending Phase 2 can test it already.
- User prefers separate exported mode classes rather than a constructor option hidden inside one class.
- User chose explicit `NuveiEnabler` mode requirement; no silent default.
- User initially asked to share everything possible, but accepted the safer boundary: share infrastructure only and keep mode lifecycle/result semantics separate.
- User wants embedded/drop-in removed entirely for now, including processor advertised/accepted methods.
- User wants the temporary `testing/` mess cleaned up now, with a proper `examples/nuvei-web-ui` npm package replacing Postman/manual sprawl.

</specifics>

<deferred>
## Deferred Ideas

- Re-adding embedded/drop-in support is deferred until sandbox evidence justifies it.
- Wallets, APMs, express payments, and stored payment methods remain out of scope.
- Production-grade shopper/billing data sourcing remains Phase 4; Phase 1.2 may use fenced sandbox placeholders only for Web SDK evidence readiness.
- Full SDK loader resilience/SRI rotation remains Phase 5 unless minimal changes are needed to split loaders safely.

</deferred>
