## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Tri-state confirmation response
- **D-01:** `POST /payments/confirm/:id` must return a tri-state business outcome: `approved`, `rejected`, or `pending`.
- **D-02:** Public response body is minimal: `{ outcome: "approved" | "rejected" | "pending" }`. No public reason codes/messages are added in this phase; detailed diagnostics stay in redacted logs.
- **D-03:** `approved` and `rejected` are definitive. `pending` means Nuvei status is inconclusive, action-required, processing, unknown, or cannot safely be written as a terminal CT transaction yet.
- **D-04:** Nuvei non-approved/inconclusive statuses must never be reported as `approved`.

#### HTTP status contract
- **D-05:** Business outcome HTTP statuses are:
  - `200` with `{ outcome: "approved" }`
  - `200` with `{ outcome: "pending" }`
  - `402` with `{ outcome: "rejected" }`
- **D-06:** `400`, `401`, `403`, and `5xx` remain request/auth/system failures, not normal payment outcomes.
- **D-07:** Enabler `apiService.confirmPayment()` must parse `402` with `{ outcome: "rejected" }` as a valid business outcome, not throw a generic technical failure.

#### Nuvei status mapping
- **D-08:** Use strict known mapping:
  - Nuvei success + approved transaction status => `approved`
  - Explicit final negative states (declined, cancelled, expired, failed/error where known final) => `rejected`
  - Unknown, action-required, processing, incomplete, ambiguous, or unevidenced states => `pending`
- **D-09:** Researcher must confirm exact Nuvei `getPaymentStatus` terminal/pending field values from official Nuvei docs, SDK behavior, or existing sandbox fixtures before planner locks the concrete mapping table. If values are not evidence-backed, classify them as `pending`, not `rejected`.

#### Canonical identifier model
- **D-10:** The connector must stop mixing `sessionToken`, optional Nuvei fiscal `transactionId` / `TransactionID`, and Nuvei payment-page `PPP_TransactionID` in the same terminal transaction field depending on success/failure.
- **D-11:** Canonical mapping:
  - CT `Payment.id` == Nuvei `merchant_unique_id`
  - CT `Payment.interfaceId` == Nuvei `sessionToken`
  - Nuvei `clientUniqueId` == CT `cartId`
  - CT terminal `Authorization` transaction `interactionId` == Nuvei `PPP_TransactionID` / `PPP_TransactionId`
- **D-12:** `sessionToken` is session/order identity. `PPP_TransactionID` is the canonical Nuvei payment attempt / terminal transaction identity for idempotency. `TransactionID` / `TransactionId` is optional fiscal transaction evidence and must not be the primary idempotency key. `clientUniqueId` is cart correlation.
- **D-13:** `PPP_TransactionID` / `PPP_TransactionId` is locked as the only canonical terminal `Authorization` `interactionId` for this connector. `TransactionID` / `TransactionId` may be stored or checked as secondary fiscal evidence, but must not be used as the primary idempotency key.
- **D-14:** If `/confirm` cannot obtain canonical `PPP_TransactionID` from Nuvei status and there is no already-recorded DMN transaction for the payment, implementation must not write a terminal CT transaction with `sessionToken` or optional fiscal `TransactionID` as a substitute. It must return `pending` unless a definitive rejected business response can be returned without CT mutation; planner must keep CT transaction writes canonical.

#### CT Payment mutation behavior
- **D-15:** Approved confirmation writes one CT `Authorization` transaction with `state: "Success"` and `interactionId` set to Nuvei `PPP_TransactionID` / `PPP_TransactionId`.
- **D-16:** Definitive rejected confirmation writes one CT `Authorization` transaction with `state: "Failure"` only when it can use canonical Nuvei `PPP_TransactionID` / `PPP_TransactionId` as `interactionId`. Duplicate confirms must not append duplicate failures.
- **D-17:** Pending confirmation should not create misleading terminal CT ledger entries. Whether to write a single deduped `Authorization Pending` is Claude/planner discretion, but the default bias is no CT transaction for pending to avoid duplicate/noisy records.
- **D-18:** Duplicate confirmation must short-circuit terminal outcomes without another CT mutation. Short-circuit logic must be based on canonical `PPP_TransactionID` / `PPP_TransactionId` identity, not on “any terminal Authorization on the Payment.”

#### Enabler behavior
- **D-19:** Add an optional `onPending` callback to the enabler-facing contract. Pending is not an error and does not call `onComplete`.
- **D-20:** `onComplete` remains final approved-only.
- **D-21:** `rejected` maps to `onError` with a safe payment rejected error.
- **D-22:** Phase 1.1.1 exposes pending but does not implement client polling. Bounded polling remains Phase 5 / SEC-02.

#### Scope fences
- **D-23:** Do not change `/payment-intents/:id` or `/webhooks/nuvei` route paths.
- **D-24:** Do not implement full Phase 3 reconciliation in this phase. This phase fixes confirmation outcome correctness and identifier ambiguity directly in the confirmation path.
- **D-25:** Do not implement bounded polling in this phase. Only expose pending so the client knows not to proceed as approved or rejected.

### Claude's Discretion
- Planner may choose exact internal TypeScript type names for the confirmation result union.
- Planner may decide whether a deduped `Authorization Pending` transaction is useful, but must not create duplicate/noisy records or write terminal records with ambiguous identifiers.
- Planner may choose the safe error class/message for rejected `onError`, following existing public safe error patterns.

### Deferred Ideas (OUT OF SCOPE)
- Bounded client polling for `pending` is deferred to Phase 5 / `SEC-02`.
- Full Phase 3 reconciliation, DMN replay protection, and global canonical field strategy beyond confirmation path remain in Phase 3.
- Sandbox proof of all Nuvei statuses remains Phase 2, but Phase 1.1.1 researcher must still confirm enough docs/evidence to safely plan this urgent bug fix.

## Summary

The current confirmation path is unsafe: the route returns `{ outcome: "approved" }` whenever `NuveiPaymentService.confirmPayment()` does not throw, and the service writes `Authorization Success` using `getPaymentStatus().transactionId` but writes `Authorization Failure` using `sessionToken`. [VERIFIED: `processor/src/routes/nuvei-payment.route.ts`, `processor/src/services/nuvei-payment.service.ts`] This violates the locked identity model because official Nuvei docs identify `PPP_TransactionID` as the mandatory payment-page transaction identifier and `TransactionID` as optional fiscal transaction evidence. [CITED: https://docs.nuvei.com/documentation/integration/webhooks/payment-dmns/]

Official Nuvei `/getPaymentStatus` output documentation lists `transactionId` as “The Gateway transaction ID” and does not list `PPP_TransactionID`/`PPP_TransactionId`/`ppp_TransactionID` in the response. [CITED: https://docs.nuvei.com/api/main/indexMain_v1_0.html?json#getPaymentStatus] Therefore the safe plan is: `/confirm` may verify Nuvei status via `sessionToken`, may return `rejected` for evidence-backed final negative status without CT terminal mutation when no PPP identity is available, but must return `pending` rather than writing a terminal CT transaction if it cannot obtain or reuse canonical PPP identity. [VERIFIED: `01.1.1-CONTEXT.md`; CITED: Nuvei API reference]

**Primary recommendation:** implement a confirmation-specific union (`approved | rejected | pending`) and canonical PPP extractor; update DMN conversion to store `PPP_TransactionID` variants as terminal `interactionId`; update enabler confirmation branching so only `approved` calls `onComplete`, `rejected` calls `onError`, and `pending` calls optional `onPending`. [VERIFIED: repository source and locked decisions]

## Common Pitfalls

### Pitfall 1: `getPaymentStatus.transactionId` looks like the right ID but is not the locked canonical ID

**What goes wrong:** Approved confirmation writes CT `Authorization Success` with `transactionId`, while DMN/operation paths use different identifiers. [VERIFIED: current service source]  
**Why it happens:** Nuvei uses similar names for Gateway/fiscal transaction IDs and payment-page PPP IDs. [CITED: Nuvei docs]  
**How to avoid:** Only use PPP variants for terminal CT `interactionId`; treat `transactionId`/`TransactionID` as secondary evidence. [VERIFIED: locked decisions]  
**Warning signs:** CT Payment has one Authorization `interactionId` equal to a UUID session token and another equal to a numeric transaction ID. [VERIFIED: current creation and confirm service]

### Pitfall 2: `402` rejected is a business response, not a fetch failure

**What goes wrong:** Enabler throws generic technical error for rejected payments because `fetch().ok` is false for 402. [VERIFIED: `enabler/src/services/api-service.ts`]  
**Why it happens:** HTTP status and payment business outcome are overloaded. [VERIFIED: locked decisions]  
**How to avoid:** Special-case `402` with valid JSON `{ outcome: "rejected" }` in `confirmPayment()`. [VERIFIED: locked decisions]  
**Warning signs:** Declined card reaches `onError` with `Failed to confirm payment: 402 ...` instead of safe payment rejected error. [INFERENCE from current code]

### Pitfall 3: Browser result may not include `sessionToken`

**What goes wrong:** Enabler sends `undefined` session token to `/confirm` if Nuvei SDK result does not echo it. [VERIFIED: current enabler code; CITED: docs examples omit `sessionToken`]  
**Why it happens:** Current `NuveiResult` type declares `sessionToken`, but official examples only show `transactionId` and result/status fields. [VERIFIED: `enabler/src/services/nuvei-sdk.ts`; CITED: Web SDK/Simply Connect docs]  
**How to avoid:** Pass the session token from `api.createPayment()` response through the component closure into `confirmPaymentResult()`. [VERIFIED: current card/drop-in code has `paymentRes.sessionToken`]  
**Warning signs:** Confirm request body contains missing or empty `sessionToken`. [INFERENCE from current code]

### Pitfall 4: Updating DMN converter is necessary for confirm idempotency

**What goes wrong:** Even if `/confirm` refuses ambiguous terminal writes, an earlier DMN still stores fiscal `TransactionID` as CT `interactionId`, so confirm cannot find canonical PPP terminal state. [VERIFIED: current converter source]  
**Why it happens:** Existing converter predates locked canonical identity model. [VERIFIED: `01.1.1-CONTEXT.md`]  
**How to avoid:** Update DMN converter/dedupe to PPP variants in this phase, while leaving full replay/security reconciliation for Phase 3. [VERIFIED: scope allows direct confirmation identifier ambiguity fix]

## Open Questions (RESOLVED)

1. **RESOLVED — Does Nuvei sandbox `getPaymentStatus` include an undocumented PPP field for Web SDK card payments?**
   - Resolution: Phase 1.1.1 plans must treat official-shaped `getPaymentStatus` responses as lacking PPP unless an actual response field matching `PPP_TransactionID`, `PPP_TransactionId`, or `ppp_TransactionID` is present. Redacted logs and enabler `onError` carry the immediate operational signal; DMN supplies canonical CT transaction identity later.
