# Phase 1.1.1: Payment confirmation tri-state outcome correctness - Context

**Gathered:** 2026-06-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix the enabler-facing payment confirmation contract so `/payments/confirm/:id` never reports Nuvei non-approved or inconclusive payment state as approved. The endpoint must expose approved, rejected, and pending outcomes, and duplicate confirmation attempts must not create duplicate terminal commercetools Payment transactions. This phase is an urgent correctness fix before sandbox validation and broader reconciliation phases.

This phase does not implement full bounded polling, final DMN reconciliation, operation-route reconciliation, or all future frontend resilience work. Those remain in later phases. It may update enabler callback contracts only as needed to expose pending safely.

</domain>

<decisions>
## Implementation Decisions

### Tri-state confirmation response
- **D-01:** `POST /payments/confirm/:id` must return a tri-state business outcome: `approved`, `rejected`, or `pending`.
- **D-02:** Public response body is minimal: `{ outcome: "approved" | "rejected" | "pending" }`. No public reason codes/messages are added in this phase; detailed diagnostics stay in redacted logs.
- **D-03:** `approved` and `rejected` are definitive. `pending` means Nuvei status is inconclusive, action-required, processing, unknown, or cannot safely be written as a terminal CT transaction yet.
- **D-04:** Nuvei non-approved/inconclusive statuses must never be reported as `approved`.

### HTTP status contract
- **D-05:** Business outcome HTTP statuses are:
  - `200` with `{ outcome: "approved" }`
  - `200` with `{ outcome: "pending" }`
  - `402` with `{ outcome: "rejected" }`
- **D-06:** `400`, `401`, `403`, and `5xx` remain request/auth/system failures, not normal payment outcomes.
- **D-07:** Enabler `apiService.confirmPayment()` must parse `402` with `{ outcome: "rejected" }` as a valid business outcome, not throw a generic technical failure.

### Nuvei status mapping
- **D-08:** Use strict known mapping:
  - Nuvei success + approved transaction status => `approved`
  - Explicit final negative states (declined, cancelled, expired, failed/error where known final) => `rejected`
  - Unknown, action-required, processing, incomplete, ambiguous, or unevidenced states => `pending`
- **D-09:** Researcher must confirm exact Nuvei `getPaymentStatus` terminal/pending field values from official Nuvei docs, SDK behavior, or existing sandbox fixtures before planner locks the concrete mapping table. If values are not evidence-backed, classify them as `pending`, not `rejected`.

### Canonical identifier model
- **D-10:** The connector must stop mixing `sessionToken`, optional Nuvei fiscal `transactionId` / `TransactionID`, and Nuvei payment-page `PPP_TransactionID` in the same terminal transaction field depending on success/failure.
- **D-11:** Canonical mapping:
  - CT `Payment.id` == Nuvei `merchant_unique_id`
  - CT `Payment.interfaceId` == Nuvei `sessionToken`
  - Nuvei `clientUniqueId` == CT `cartId`
  - CT terminal `Authorization` transaction `interactionId` == Nuvei `PPP_TransactionID` / `PPP_TransactionId`
- **D-12:** `sessionToken` is session/order identity. `PPP_TransactionID` is the canonical Nuvei payment attempt / terminal transaction identity for idempotency. `TransactionID` / `TransactionId` is optional fiscal transaction evidence and must not be the primary idempotency key. `clientUniqueId` is cart correlation.
- **D-13:** `PPP_TransactionID` / `PPP_TransactionId` is locked as the only canonical terminal `Authorization` `interactionId` for this connector. `TransactionID` / `TransactionId` may be stored or checked as secondary fiscal evidence, but must not be used as the primary idempotency key.
- **D-14:** If `/confirm` cannot obtain canonical `PPP_TransactionID` from Nuvei status and there is no already-recorded DMN transaction for the payment, implementation must not write a terminal CT transaction with `sessionToken` or optional fiscal `TransactionID` as a substitute. It must return `pending` unless a definitive rejected business response can be returned without CT mutation; planner must keep CT transaction writes canonical.

### CT Payment mutation behavior
- **D-15:** Approved confirmation writes one CT `Authorization` transaction with `state: "Success"` and `interactionId` set to Nuvei `PPP_TransactionID` / `PPP_TransactionId`.
- **D-16:** Definitive rejected confirmation writes one CT `Authorization` transaction with `state: "Failure"` only when it can use canonical Nuvei `PPP_TransactionID` / `PPP_TransactionId` as `interactionId`. Duplicate confirms must not append duplicate failures.
- **D-17:** Pending confirmation should not create misleading terminal CT ledger entries. Whether to write a single deduped `Authorization Pending` is Claude/planner discretion, but the default bias is no CT transaction for pending to avoid duplicate/noisy records.
- **D-18:** Duplicate confirmation must short-circuit terminal outcomes without another CT mutation. Short-circuit logic must be based on canonical `PPP_TransactionID` / `PPP_TransactionId` identity, not on “any terminal Authorization on the Payment.”

### Enabler behavior
- **D-19:** Add an optional `onPending` callback to the enabler-facing contract. Pending is not an error and does not call `onComplete`.
- **D-20:** `onComplete` remains final approved-only.
- **D-21:** `rejected` maps to `onError` with a safe payment rejected error.
- **D-22:** Phase 1.1.1 exposes pending but does not implement client polling. Bounded polling remains Phase 5 / SEC-02.

### Scope fences
- **D-23:** Do not change `/payment-intents/:id` or `/webhooks/nuvei` route paths.
- **D-24:** Do not implement full Phase 3 reconciliation in this phase. This phase fixes confirmation outcome correctness and identifier ambiguity directly in the confirmation path.
- **D-25:** Do not implement bounded polling in this phase. Only expose pending so the client knows not to proceed as approved or rejected.

### Claude's Discretion
- Planner may choose exact internal TypeScript type names for the confirmation result union.
- Planner may decide whether a deduped `Authorization Pending` transaction is useful, but must not create duplicate/noisy records or write terminal records with ambiguous identifiers.
- Planner may choose the safe error class/message for rejected `onError`, following existing public safe error patterns.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `PaymentModificationStatus` currently provides `APPROVED` and `REJECTED`; it may need a `PENDING` value or a new confirmation-specific outcome union.
- `PaymentSetupError` / public error patterns from Phase 1 can be reused for safe `onError` when confirm returns rejected.
- Existing `assertSessionPaymentAccess()` validates session token belongs to the Payment and authenticated cart before confirm proceeds.
- Existing `assertNuveiStatusMatchesPayment()` validates client/cart, amount, and currency when fields are present.

### Established Patterns
- CT Payment `interfaceId` stores the Nuvei session token from `openOrder`.
- DMN processing currently treats optional Nuvei `TransactionID` as the transaction `interactionId` and `pspReference`; this must be revised to prefer mandatory `PPP_TransactionID` / `PPP_TransactionId` for canonical idempotency.
- Capture/cancel/refund prefer the successful Authorization transaction `interactionId`, falling back to `payment.interfaceId` only when no successful authorization exists; after this phase, successful Authorization `interactionId` should be canonical `PPP_TransactionID`, not session token.
- Current confirm route catches thrown errors and returns rejected; it does not inspect service outcome.

### Integration Points
- Processor route: `POST /payments/confirm/:id` must map service result to 200/402 and tri-state body.
- Processor service: `NuveiPaymentService.confirmPayment()` must return tri-state outcome and enforce canonical identifier writes/deduplication.
- Enabler: `confirmPaymentResult()` must branch on approved/rejected/pending; add optional `onPending` callback and keep `onComplete` approved-only.
- Tests: service, route, and enabler API tests are all directly affected.

</code_context>

<specifics>
## Specific Ideas

- User explicitly rejected using mixed identifiers in `transactions[].interactionId`: “We MUST always use the same type of identifier in the SAME field.”
- User’s resolved model: `Payment.interfaceId` should be `sessionToken`; terminal `transactions[].interactionId` should be mandatory Nuvei `PPP_TransactionID`; `clientUniqueId` maps to cart ID; optional fiscal `TransactionID` is secondary evidence, not the canonical idempotency key.
- User locked the model after noting Nuvei `transactionId` / DMN `TransactionID` is optional, while `PPP_TransactionID` is a mandatory unique 64-bit DMN identifier. The canonical identity model is resolved: terminal `transactions[].interactionId` uses `PPP_TransactionID`, never `sessionToken` or optional fiscal `TransactionID`.
- User selected `402` for rejected business outcome, with the required caveat that enabler must parse 402 rejected as a business result, not as a generic technical failure.

</specifics>
