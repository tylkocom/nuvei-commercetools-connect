# Phase 1.1.1: Payment confirmation tri-state outcome correctness - Validation

**Created:** 2026-06-02
**Status:** Ready for execution

## Validation Architecture

Phase 1.1.1 changes payment confirmation semantics across processor, enabler, and manual assets. Validation is split by execution wave so each wave proves its own contract before the next wave consumes it.

### Wave 1: Processor confirmation and canonical PPP identity

**Plan:** `01.1.1-01-PLAN.md`

**Primary risks validated:**
- Nuvei non-approved or inconclusive status is never returned as `approved`.
- `/payments/confirm/:id` returns only `{ outcome: "approved" | "rejected" | "pending" }`.
- HTTP mapping is `200 approved`, `200 pending`, `402 rejected`.
- Technical/session/cart/request failures are not encoded as business `rejected`.
- Terminal CT `Authorization` transaction `interactionId` is canonical Nuvei `PPP_TransactionID` / `PPP_TransactionId` / `ppp_TransactionID` only.
- No terminal CT transaction writes use `sessionToken` or optional fiscal `transactionId` / `TransactionID` fallback.
- DMN conversion and duplicate detection use canonical PPP identity, not optional fiscal `TransactionID`.

**Automated check:**

```bash
npm run test --prefix processor -- test/unit/services/nuvei-payment.service.test.ts test/unit/routes/nuvei-payment.route.test.ts
```

**Required behavioral coverage:**
- approved with canonical PPP writes one Success Authorization using PPP as `interactionId`.
- approved official-shaped status without PPP returns pending and writes no CT terminal transaction.
- rejected final negative without PPP returns rejected and writes no CT terminal transaction.
- rejected final negative with canonical PPP writes one Failure Authorization using PPP as `interactionId`.
- duplicate approved/rejected canonical PPP short-circuits without duplicate `updatePayment`.
- pending/unknown/missing/action-required values return pending and write no terminal CT transaction.
- session/cart/amount/currency mismatch remains a technical failure.
- route maps service outcomes to `200/200/402` and does not convert thrown technical errors to business rejected.
- DMN fixtures/converter accept PPP variants and treat optional fiscal ID as secondary evidence.

### Wave 2: Enabler tri-state parsing and callbacks

**Plan:** `01.1.1-02-PLAN.md`

**Primary risks validated:**
- `apiService.confirmPayment()` parses valid `402 { outcome: "rejected" }` as a business outcome.
- Non-402 non-2xx responses remain technical/request failures.
- `onComplete` is approved-only.
- `rejected` calls safe `onError` and never `onComplete`.
- `pending` calls optional `onPending` and never `onComplete` or `onError`.
- Card and embedded drop-in pass the known session token from `createPayment()` response, not an untrusted/missing browser SDK result token.
- No bounded polling is introduced.

**Automated check:**

```bash
npm run test --prefix enabler -- test/unit/api-service.test.ts test/unit/card.test.ts test/unit/dropin.test.ts test/unit/payment-enabler.test.ts
```

### Wave 3: Documentation and manual assets

**Plan:** `01.1.1-03-PLAN.md`

**Primary risks validated:**
- Docs and local testing assets describe approved/rejected/pending confirmation behavior.
- Docs and Postman reflect `200 approved`, `200 pending`, `402 rejected`.
- Docs expose `onPending` and approved-only `onComplete`.
- Manual assets do not instruct terminal CT writes with `sessionToken` or optional fiscal `TransactionID` fallback.
- `/payment-intents/:id` and `/webhooks/nuvei` paths remain unchanged.
- No stale `/payments/confirmPayments/:id` guidance remains.

## Phase Gate

After all waves complete, phase verification should inspect source and summaries for these non-negotiable truths:

1. `/payments/confirm/:id` cannot false-approve Nuvei rejected/pending/inconclusive status.
2. Business outcomes are tri-state with minimal response body.
3. `402 rejected` is handled by the enabler as a business outcome.
4. Pending is exposed via optional `onPending`; no polling is implemented.
5. Terminal CT Authorization `interactionId` uses canonical PPP identity only.
6. DMN conversion/deduplication no longer depends on optional fiscal `TransactionID` as the primary idempotency key.
7. No route changes are made to `/payment-intents/:id` or `/webhooks/nuvei`.
8. Docs and Postman match the implemented behavior.
