# Phase 1.1.1 Plan 02: Summary

**Enabler tri-state confirmation: 402 parsed as rejected, processor outcome routes approved/rejected/pending callbacks, card and drop-in confirm with known session token from createPayment**

## Accomplishments

- `ConfirmPaymentResponse.outcome` narrowed from `string` to `"approved" | "rejected" | "pending"`
- `apiService.confirmPayment` parses HTTP 402 + `{ outcome: "rejected" }` as a valid business result (not throw); malformed 402 and all other non-ok statuses still throw
- `confirmPaymentResult` rebuilt with explicit `knownSessionToken` parameter; branches exclusively on processor outcome: approved → `onComplete`, rejected → safe `PaymentSetupError`, pending → optional `onPending`
- Browser SDK `transactionStatus` no longer gates the processor call or any callback
- `EnablerOptions.onPending` and `PendingPaymentResult` type added
- `CardComponent` and `DropinComponents` both pass `paymentRes.sessionToken` to confirmation, not `result.sessionToken`
- 9 new RED tests covering 402 parsing, callback routing, and session-token handoff; all 57 targeted tests green after implementation

## Decisions Made

- `PendingPaymentResult` is a separate type from `PaymentResult` to avoid conflation with `isSuccess` semantics
- Rejected `onError` wraps a `PaymentSetupError` with `REQUEST_MALFORMED` code and a generic user-facing message — no session token, no Nuvei status string, no raw diagnostics in the public error (T-01.1.1-08)
- `confirmPaymentResult` signature adds `knownSessionToken` as 3rd positional argument (before `api`) to make the source-of-truth explicit at every callsite
- Browser `result.transactionStatus` check removed entirely — processor outcome is the only gate for all callbacks
