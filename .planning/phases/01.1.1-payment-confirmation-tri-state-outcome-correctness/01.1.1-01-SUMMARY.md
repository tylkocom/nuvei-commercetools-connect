# Phase 1.1.1 Plan 01: Summary

**Tri-state confirmation (approved|rejected|pending) with canonical PPP terminal writes; /confirm never uses sessionToken or fiscal transactionId as CT Authorization interactionId**

## Performance

- **Duration:** 7 min
- **Started:** 2026-06-02T21:12:26Z
- **Completed:** 2026-06-02T21:19:59Z
- **Tasks:** 2 (TDD RED + GREEN)

## Accomplishments

- `POST /confirm/:id` now returns `{ outcome: "approved" | "rejected" | "pending" }` with 200/200/402
- Approved official-shaped Nuvei status (no PPP) returns `pending` with no CT terminal write
- Rejected without PPP returns `rejected` without CT terminal write; with PPP writes one Failure Authorization
- Duplicate canonical PPP short-circuits without appending another CT transaction
- `classifyNuveiStatus()` and `extractCanonicalPpp()` added as pure module-level helpers
- DMN converter updated to use PPP as `interactionId` and `pspReference`; fiscal `TransactionID` optional
- DMN deduplication updated to PPP-based (was fiscal `TransactionID`)
- 19 new RED tests added in Task 1; all 61 targeted tests green after Task 2; 128/128 full suite green

## Decisions Made

- Confirmation-specific `PaymentConfirmResponseSchema` DTO added instead of widening `PaymentIntentResponseSchema`
- No `Authorization Pending` CT transaction written for pending outcome (D-17 default bias)
- `PPP_TRANSACTION_ID_KEYS` constant defined at module level as single source of truth for all three documented PPP variants
- `classifyNuveiStatus` and `extractCanonicalPpp` are module-level pure functions, not class methods (no state dependency)
- Fiscal `transactionId` comparison removed entirely from `assertDmnMatchesNuveiStatus`; remaining validations (session, client, amount, currency) are still enforced

## Issues Encountered

- `assertDmnMatchesNuveiStatus` previously required `statusBody.transactionId === updateData.pspReference`. After making `pspReference` PPP-based, this comparison becomes `fiscal_id !== PPP_value` which always fails. Removing this comparison per research recommendation (D-12) is correct — the session token, clientUniqueId, amount, and currency cross-checks are sufficient for DMN validation integrity.
