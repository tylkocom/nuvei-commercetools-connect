## Summary

This phase is entirely surgical: rename two route path strings, drop one route, add one route, remove one duplicate schema, fix one type primitive, and update all callers. No new business logic. No new external dependencies.

The processor uses `@fastify/autoload` to register plugins from `processor/src/server/plugins/`. The two relevant plugins are `operation.plugin.ts` (no prefix, routes: `/config`, `/status`, `/payment-components`, `/payment-intents/:id`, `/transactions`) and `nuvei-payment.plugin.ts` (prefix `/payments` for payment routes, prefix `/webhooks` for webhook routes). Route path changes are single-string edits inside `nuvei-payment.route.ts`.

The `GET /health` endpoint follows the same registration pattern as the operations routes — inline inside `operationsRoute` in `operation.route.ts`, no prefix, no auth `preHandler`. The health logic is a synchronous config-var scan that does **not** use `statusHandler` from `connect-payments-sdk` (that is heavier and requires live network calls; `/health` is intentionally static).

**Primary recommendation:** All seven decisions can be implemented in six files plus the Postman JSON. No architectural changes, no new packages.

## Architecture Patterns

### How Fastify routes are registered in this project

```
setupFastify()
  └── @fastify/autoload loads processor/src/server/plugins/
        ├── operation.plugin.ts  → server.register(operationsRoute, { ... })
        │     No prefix → routes live at /config, /status, /payment-components,
        │                          /payment-intents/:id, /transactions
        └── nuvei-payment.plugin.ts
              ├── server.register(paymentRoutes, { prefix: '/payments', ... })
              │     Routes live at /payments/*, /payments/confirmPayments/:id, etc.
              └── server.register(nuveiWebhookRoutes, { prefix: '/webhooks', ... })
                    Routes live at /webhooks/nuvei
```

**Implication:** All route path string changes are inside the `paymentRoutes` function in `nuvei-payment.route.ts`. The plugin prefixes in `nuvei-payment.plugin.ts` do not change.

**Adding `/health`:** Register `fastify.get('/health', ...)` inside `operationsRoute` in `operation.route.ts`. Because `operation.plugin.ts` registers `operationsRoute` with no prefix, the final path is `/health`. No new plugin file needed.

```typescript
const HealthCheckItemSchema = Type.Object({

```

### How statusHandler works (and why NOT to use it for /health)

`statusHandler` from `connect-payments-sdk` has this signature:
```typescript
export declare const statusHandler: (opts: StatusHandlerOpts) => () => Promise<HandlerResponse<HealthCheckStatus>>;

type StatusHandlerOpts = {
  timeout: number;
  checks: HealthCheck[];     // each check: () => Promise<HealthCheckResult>
  metadataFn?: () => Promise<object> | object;
  log: Logger;
};

type HealthCheckStatus = {
  status: 'OK' | 'Partially Available' | 'Unavailable';
  timestamp: string;
  checks: HealthCheckResult[];
  version: string;
  metadata?: object;
};
```

`/status` already uses it with two live checks (CT permissions, Nuvei reachability) and a `timeout`. The response type uses `'OK'|'Partially Available'|'Unavailable'` strings and includes `timestamp`/`version` fields. This is richer but heavier — requires network round-trips and a full logger.

`/health` per D-10/D-11 is a **config-only check**. Using `statusHandler` would be over-engineering: it would trigger network calls for an endpoint intended as a lightweight infra probe. Use a plain service method instead.

### Health check implementation pattern

```typescript
// processor/src/services/nuvei-payment.service.ts
public async health(): Promise<HealthResponseDTO> {
  const config = getConfig();
  const requiredVars: Array<{ name: string; value: string }> = [
    { name: "CTP_PROJECT_KEY",     value: config.projectKey },
    { name: "CTP_CLIENT_ID",       value: config.clientId },
    { name: "CTP_CLIENT_SECRET",   value: config.clientSecret },
    { name: "CTP_AUTH_URL",        value: config.authUrl },
    { name: "CTP_API_URL",         value: config.apiUrl },
    { name: "CTP_SESSION_URL",     value: config.sessionUrl },
    { name: "CTP_CHECKOUT_URL",    value: config.checkoutUrl },
    { name: "CTP_JWKS_URL",        value: config.jwksUrl },
    { name: "CTP_JWT_ISSUER",      value: config.jwtIssuer },
    { name: "NUVEI_MERCHANT_ID",   value: config.nuveiMerchantId },
    { name: "NUVEI_MERCHANT_SITE_ID", value: config.nuveiMerchantSiteId },
    { name: "NUVEI_SECRET_KEY",    value: config.nuveiSecretKey },
    { name: "NUVEI_API_BASE_URL",  value: config.nuveiApiBaseUrl },
  ];

  const checks = requiredVars.map(({ name, value }) => ({
    name,
    status: (value && value !== "xxx") ? ("ok" as const) : ("failed" as const),
  }));

  return {
    status: checks.every((c) => c.status === "ok") ? "ok" : "degraded",
    checks,
  };
}
```

Note: since `validateConfig()` runs at server start and throws on missing values, in practice `/health` will almost always return `{ status: 'ok' }` if the server is running. The value is for operators who want a structured endpoint to probe rather than relying on startup logs.

The `health()` method must be added as `abstract health(): Promise<HealthResponseDTO>` on `AbstractPaymentService`.

## Common Pitfalls

### Pitfall 1: Double-prefix on the renamed session route
**What goes wrong:** If `nuvei-payment.plugin.ts` prefix is changed from `/payments` to something else, or if the route path inside `paymentRoutes` is changed to `/payments/session` (already includes prefix), the final path becomes `/payments/payments/session`.
**How to avoid:** The plugin prefix `/payments` stays unchanged. Only the route string inside `paymentRoutes` changes from `"/"` to `"/session"`. The concatenation produces `/payments/session` as intended.

### Pitfall 2: Removing `getPayment` breaks callers
**What goes wrong:** Deleting `getPayment` from `ApiService` type causes TypeScript errors if any consumer casts to `ApiService` and expects `getPayment`.
**Root cause:** `getPayment` is in the `ApiService` type but is never called by `card.ts` or `dropin-embedded.ts`. However, tests or other consumers might reference it.
**Verified safe:** Grep confirms no test file or component file calls `api.getPayment()`. The method is exposed but unused.

### Pitfall 3: Route test still references old path string
**What goes wrong:** `processor/test/unit/routes/nuvei-payment.route.test.ts` tests the handler by extracting routes from a test double (not Fastify's real router). The test looks up `app.routes.find((r) => r.method === "POST" && r.url === "/")`. After renaming `"/"` → `"/session"`, the lookup `url === "/"` must become `url === "/session"`.
**Impact:** The existing test for `POST /` will break at test extraction if the URL filter is not updated.

### Pitfall 4: `$id: "paramsSchema"` collision when two routes use it
**What goes wrong:** Both `/confirmPayments/:id` and `/payment-intents/:id` define inline params schema with `$id: "paramsSchema"`. After renaming, both `/confirm/:id` and `/payment-intents/:id` will still have this — they are registered in different Fastify plugins (different instances), so no conflict in practice. But if the paths were ever merged into one plugin, this would cause a schema collision.
**How to avoid:** Rename the `$id` from `"paramsSchema"` to a more specific identifier in the confirm route: `"confirmParamsSchema"`. This is a cheap, safe improvement.

### Pitfall 5: Postman "dropin" body still used elsewhere
**What goes wrong:** D-16 changes `"dropin"` → `"embedded"` in item "04 Processor Create Dropin Payment Intent". If the description still says "drop-in for embedded" without clarifying `"embedded"` is the valid key, future testers may be confused.
**How to avoid:** Update both the body and the description string.

## Code Examples

### Correct Fastify route with no auth (health endpoint pattern)

No existing auth-free routes in the codebase today — `/health` will be the first. The pattern is simply omitting `preHandler`:

```typescript
// Source: established project pattern in operation.route.ts (auth routes) + Fastify docs
fastify.get<{ Reply: HealthResponseSchemaDTO }>(
  "/health",
  {
    schema: {
      response: {
        200: HealthResponseSchema,
      },
    },
  },
  async (_, reply) => {
    const result = await opts.paymentService.health();
    return reply.status(200).send(result);
  },
);
```

Compared to `/config` (which has `preHandler: [opts.sessionHeaderAuthHook.authenticate()]`), the health route simply has no `preHandler` key at all. Fastify treats the absence as "no authentication required."

### TypeBox schema for health response

```typescript
// processor/src/dtos/operations/health.dto.ts
import { Static, Type } from "@sinclair/typebox";

export const HealthCheckItemSchema = Type.Object({
  name: Type.String(),
  status: Type.Union([Type.Literal("ok"), Type.Literal("failed")]),
});

export const HealthResponseSchema = Type.Object({
  status: Type.Union([Type.Literal("ok"), Type.Literal("degraded")]),
  checks: Type.Array(HealthCheckItemSchema),
});

export type HealthResponseSchemaDTO = Static<typeof HealthResponseSchema>;
```

HTTP 200 in all cases (including degraded). The `status` field is the machine-readable signal. Infra probes read `status === 'ok'` rather than checking HTTP status codes, so non-2xx would cause false-alarm alerts on monitoring systems.


1. **Should `createPaymentIntent` be renamed to `createPaymentSession` in the service layer?**
   - What we know: D-08 says "service methods … must use [Nuvei language]". `createPaymentIntent` maps a Stripe concept onto a Nuvei `openOrder` call.
   - What's unclear: Whether "service methods" in D-08 specifically targets the session-creation method or only the modification methods (capture/cancel/refund/reverse, which already use correct names).
   - Recommendation: Include the rename. It's an internal-only method name, and renaming while the route is already being changed keeps the cleanup atomic. Callers: only `nuvei-payment.route.ts` (one call site in the route handler).

2. **Should `PaymentIntentRequestSchema` / `PaymentIntentResponseSchema` in `payment-intents.dto.ts` be renamed?**
   - What we know: These schemas describe the CT Checkout payment-intents API endpoint body/response. The endpoint path `/payment-intents/:id` is preserved (D-07).
   - Recommendation: Do NOT rename. The "PaymentIntent" in those schema names refers to the CT API contract, not Nuvei internals. Renaming them would obscure the connection to the CT Checkout spec.
