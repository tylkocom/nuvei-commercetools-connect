# Phase 1.1: Processor API design cleanup and health endpoint - Context

**Gathered:** 2026-06-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Clean up the processor's HTTP API surface to remove Stripe-template naming and inconsistencies introduced without critical review. Add a `GET /health` endpoint for unauthenticated infrastructure probes. All changes must preserve required commercetools Checkout compatibility. No new payment capabilities introduced.

</domain>

<decisions>
## Implementation Decisions

### Route naming — confirm endpoint
- **D-01:** Rename `POST /payments/confirmPayments/:id` → `POST /payments/confirm/:id`. The `:id` parameter is the CT Payment ID (paymentReference). camelCase URL is the only inconsistency in the API surface; all other routes are kebab-case.
- **D-02:** Enabler `api-service.ts` must be updated to call `/payments/confirm/:id` instead of `/payments/confirmPayments/:id`.
- **D-03:** Postman collection must be updated to use the new path.

### Route naming — payment session creation
- **D-04:** Replace `GET /payments` and `POST /payments` with `POST /payments/session`. The GET variant was backward-compat only and is dropped. POST with no body is still valid (defaults to `card`).
- **D-05:** Enabler `api-service.ts` must be updated to `POST /payments/session`.
- **D-06:** Postman collection must be updated.

### Route naming — payment-intents
- **D-07:** `POST /payment-intents/:id` path is **preserved unchanged**. The commercetools Checkout Payment Intents API proxies directly to this path on the processor (confirmed from CT docs: `POST https://checkout.{region}.commercetools.com/{projectKey}/payment-intents/{paymentId}`). Renaming would break CT Checkout integration.
- **D-08:** Internal naming only is cleaned up: service methods, DTO type names, and code comments must use `capturePayment`/`cancelPayment`/`refundPayment`/`reversePayment` language instead of Stripe-flavoured "PaymentIntent" terminology.

### Webhook route
- **D-09:** `POST /webhooks/nuvei` is preserved unchanged. PSP-specific naming is correct; the path is already configured in the Nuvei dashboard and Postman collection.

### Health endpoint
- **D-10:** Add `GET /health` — **no authentication required**. Returns `{ status: 'ok'|'degraded', checks: [...] }` where checks cover: required config env vars present and non-empty.
- **D-11:** `GET /health` is separate from `GET /status`. `/status` requires JWT auth and performs live CT permissions check + Nuvei reachability. `/health` is for infra/Connect probes that have no Checkout session JWT.
- **D-12:** `GET /status` is kept unchanged (JWT auth, full CT + Nuvei readiness via `statusHandler`). Its `metadata.name` already correctly returns `@nuvei-commercetools/processor`; no changes needed there.

### DTO and schema fixes
- **D-13:** Remove duplicate `PaymentConfirmRequestSchema` — it exists in both `nuvei-payment.dto.ts` and `payment-intents.dto.ts`. Single source of truth: `nuvei-payment.dto.ts`. The copy in `payment-intents.dto.ts` (`PaymentIntentConfirmRequestSchema`) is removed and all importers updated.
- **D-14:** `centAmount` must use `Type.Integer()` everywhere, not `Type.Number()`. Fix `transaction.dto.ts` to match `payment-intents.dto.ts` (which already uses Integer).
- **D-15:** Enabler `PaymentSessionResponse` type must include `cartId` field to match the processor's actual response shape. The processor returns `{ cartId, sessionToken, paymentReference, merchantReturnUrl }`; the enabler type currently omits `cartId`.
- **D-16:** Postman collection must replace the `dropin` payment method key with `card` or `embedded`. The processor rejects `dropin` — only `card` and `embedded` are valid keys.

### Claude's Discretion
- Response shape for `GET /health` — exact field names, HTTP status codes for degraded state (200 with `status: 'degraded'` vs 503), and check naming are left to the implementer. Prefer 200 with `status` field over non-2xx so infra probes don't false-alarm.
- Whether to add a Fastify route plugin for `/health` or register it inline in `operation.route.ts` — use the existing pattern.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `statusHandler` from connect-payments-sdk: already used in `nuvei-payment.service.ts:status()`. The same pattern (checks array, metadataFn) can be used for `/health` with a config-check function.
- `JWTAuthenticationHook`, `SessionHeaderAuthenticationHook` from connect-payments-sdk: existing auth hooks; `/health` explicitly uses neither.
- `PublicPaymentErrorSchema` in `payment-errors.dto.ts`: reuse error code pattern for any new error responses.

### Established Patterns
- Route handlers delegate to `paymentService` methods; `/health` should follow the same pattern (add a `health()` method on `AbstractPaymentService` and `NuveiPaymentService`).
- All routes use TypeBox schemas for request/response validation via `@fastify/type-provider-typebox`.
- Routes are grouped into plugins registered in `nuvei-payment.plugin.ts` and `operation.plugin.ts`.

### Integration Points
- Enabler `api-service.ts` calls processor directly with `X-Session-ID` header; path changes in D-04 and D-01 must be reflected there.
- Postman collection is the manual testing surface; all route changes need corresponding collection updates.
- `docs/ARCHITECTURE.md` documents the current API; update it to reflect renamed and new routes.

</code_context>

<specifics>
## Specific Ideas

- User confirmed: commercetools docs were checked in-session before the `/payment-intents/:id` decision. The platform contract was the deciding factor, not preference.
- User confirmed: `/status` being fully wired (not a stub) was discovered during discussion. The decision to add `/health` separately was made with full knowledge of what `/status` already does.
- The "payment intent" terminology in comments/service method names is the specific naming drift to eliminate — it maps Stripe concepts onto Nuvei concepts. The correct Nuvei language is: openOrder creates a session, confirmPayment validates it, capture/cancel/refund operate on the authorized transaction.

</specifics>
